Plan · Inputs, processing, outputs

Where we are going, one milestone at a time.

An agent produces memories, a CLI publishes them with typed attributes, the kernel module deduplicates, indexes and versions them, and any program reads them back as ordinary files. Pick a milestone to see which parts exist at that point.

Green boxes are validated in an isolated Linux VM. Everything else is proposed in ADR-0005 and the roadmap; none of it is implemented or measured.

How to read the plan

  • The middle column is where MoobFS exists. Input and output are contracts with the outside world; the project's contribution is what happens inside the kernel between them.
  • M2 carries most of the technical risk. PUT, transactions, indexes, xattr and QUERY all depend on it.
  • M4 closes the loop without kernel code. Semantic retrieval and context assembly stay in the agent application, as decided in ADR-0005.

Free software already covers several steps: dm-log-writes and xfstests for crash testing, virtme-ng for instrumented kernels, Haiku's bfs_shell as a behavioral oracle for queries. See the ecosystem survey.

Status: only M1 is implemented and tested. The other boxes describe intent, not behavior. Each will require a format specification, invalid-input tests and an explicit compatibility decision before code.
