From bytes to a mounted filesystem.

MoobFS is aimed at persistent LLM memory and context. This guide reproduces the storage foundation implemented today: create an image, inspect shared objects and run the native Linux module in an isolated VM.

Agent memory retrieval and context assembly are future work. This experiment verifies file reads and physical sharing; it does not yet demonstrate an LLM consuming memories. Read the project goal and division of responsibilities →

1. Create and inspect an image

You need a C11 compiler, Make and Python 3 on Linux or macOS. Run from the repository root:

git clone https://github.com/studiomoob/llmoobfs.git
cd llmoobfs
make test
printf 'A shared memory.\n' > build/memory.txt
build/host/mkfs.moobfs build/demo.img \
  alpha.txt=build/memory.txt beta.txt=build/memory.txt
build/host/fsck.moobfs build/demo.img

The verifier emits JSON. Look for different inode numbers referencing the same object ID and physical offset. The creator compares full bytes before deduplicating, and refuses to overwrite an existing image. Use a new output filename when repeating the demo.

fsck.moobfs validates; it does not repair. The small example above has different sizes from the larger automated fixture below.

2. Run the native Linux test

Start Docker, then run:

make vm-test

The harness compiles against Linux 6.12.111+deb13-amd64 and boots that exact kernel in QEMU. It loads the module there, creates loop-backed mounts, reads both files and checks their shared extent. No privileged container or host module loading is required.

The first run downloads compiler and kernel packages. Apple Silicon uses x86 CPU emulation. The QEMU test phase times out after 180 seconds; the initial build can take longer.

For manual VM mounting, sanitizer commands and troubleshooting, use the complete testing guide.

3. Read the evidence

The automated fixture has a 12,562-byte logical payload. The two files reference one 16,384-byte aligned allocation. A successful run contains:

SHARED: inode=2/3 physical=12288 length=16384
MOUNTED_READ_TESTS_PASS
WRITABLE_MOUNT_REJECTED
MOOBFS_VM_PASS: shared extents, independent inodes, reads,
readonly, remount, 15 malformed images

The last marker is printed on a single line. Expected “Invalid argument” mount errors correspond to deliberately malformed images. Writable mount attempts are also expected to fail.

The first local validation is recorded in the engineering journal. Future results are visible in CI runs.

Know the boundary of the result

  • Flat namespace; at most 128 files/objects and 64 KiB per object.
  • Printable ASCII filenames up to 63 bytes; file contents may contain any bytes.
  • Read-only images, fully checked during mount. Keep the backing image unchanged while mounted.
  • Separate inodes may have separate cached pages despite sharing physical storage.
  • No writes, mmap, direct I/O, transactions, snapshots, encryption or agent retrieval.
  • No measured performance advantage. The distribution test kernel has KASAN and PROVE_LOCKING disabled.

The M1 disk format is experimental and distinct from the future transactional proposal. Kernel API compatibility is only tested for the pinned target.
